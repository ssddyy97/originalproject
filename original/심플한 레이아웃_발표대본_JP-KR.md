## 10페이지 — 중복 예약 방지

**일본어 발표문 · 약 55초**

最も工夫したのは、重複予約を二段階で防ぐ仕組みです。
まず、アプリケーション側で、同じ会議室に時間帯が重なる予約がないか確認します。
ただし、確認した直後に別のリクエストが入ると、両方が「空いている」と判断する可能性があります。
そこで、PostgreSQLにも、同じ会議室で予約時間が重ならないようにする排他制約を設けました。
アプリケーションの確認をすり抜けても、最後はデータベースで重複を防ぎます。
なお、対象は確定済みの予約だけなので、キャンセル後は同じ時間帯を再び予約できます。

**한국어 뜻**

가장 공들인 부분은 중복 예약을 두 단계로 방지하는 구조입니다. 먼저 앱에서 같은 회의실에 시간이 겹치는 예약이 있는지 확인합니다. 다만 확인 직후 다른 요청이 들어오면 양쪽 모두 비어 있다고 판단할 수 있습니다. 그래서 PostgreSQL에도 같은 회의실의 예약 시간이 겹치지 않도록 배제 제약을 설정했습니다. 앱 검사를 통과하더라도 DB가 최종적으로 중복을 막습니다. 확정된 예약만 대상이므로 취소 후에는 같은 시간을 다시 예약할 수 있습니다.

## 12페이지 — 동시 요청 테스트

**일본어 발표문 · 약 40초**

この仕組みを確認するために、同じ会議室、同じ時間帯へ、10件の予約リクエストを同時に送るテストを行いました。
スライドに示した結果では、1件が作成成功の201、残り9件が競合を示す409となり、データベースに保存された予約も1件でした。
レスポンスだけでなく、実際の保存件数も確認しています。

**한국어 뜻**

## 13페이지 — CI/CD와 배포

**일본어 발표문 · 약 40초**

配備には、GitHub Actionsを使いました。
mainブランチへのプッシュをきっかけに、GitHub側でテストとビルドを実行し、作成したJARファイルを保存します。
その後、サーバー側のセルフホステッドランナーが、その成果物を使って配備します。
ポイントは、テストとビルドを通過した成果物を、そのままサーバーへ渡すことです。
サーバーでは、Nginx、Spring Boot、PostgreSQLを組み合わせて動かす構成にしました。

**한국어 뜻**

배포에는 GitHub Actions를 사용했습니다. main 브랜치에 push하면 GitHub 측에서 테스트와 빌드를 실행하고 생성된 JAR 파일을 저장합니다. 이후 서버의 셀프 호스티드 러너가 그 결과물로 배포합니다. 핵심은 테스트와 빌드를 통과한 결과물을 그대로 서버에 전달한다는 점입니다. 서버는 Nginx, Spring Boot, PostgreSQL을 조합한 구성입니다.

## 14페이지 — 배포 중 문제 해결

**일본어 발표문 · 약 50초**

配備では、ローカル環境では起きなかった問題にも直面しました。
一つ目は、ランナーの認証失敗です。VMの時刻ずれが原因だったため、chronyで時刻を同期しました。
二つ目は、systemdの実行エラーです。SELinuxによる実行制限を確認し、配置先とセキュリティコンテキストを見直しました。
三つ目は、Nginxの502エラーです。こちらもログから通信制限を確認し、必要な通信を許可する設定を行いました。
この経験から、エラーメッセージだけで判断せず、ログを根拠に原因を絞り込むことの大切さを学びました。

**한국어 뜻**

배포 중에는 로컬에서 발생하지 않았던 문제도 만났습니다. 첫째는 러너 인증 실패로, VM의 시간 차이가 원인이어서 chrony로 동기화했습니다. 둘째는 systemd 실행 오류로, SELinux의 실행 제한을 확인해 배치 경로와 보안 컨텍스트를 조정했습니다. 셋째는 Nginx 502 오류로, 로그에서 통신 제한을 확인하고 필요한 통신을 허용했습니다. 이 경험을 통해 오류 메시지만으로 판단하지 않고 로그를 근거로 원인을 좁혀가는 중요성을 배웠습니다.

### ③ 재조회

次に、予約情報を再取得します。
登録した予約が再び表示されることを確認できます。

→ 재조회 기능 또는 새로고침 후 동일한 회의실·날짜로 예약을 확인합니다.

### ④ 중복 방지 확인 — 실제로 준비된 방식에 맞춰 선택

**화면에서 예약된 시간대를 선택할 수 없는 경우:**

予約済みの時間帯は、画面からは選択できないようになっています。
なお、同時リクエストに対する制御は、先ほどのAPIテストで確認しています。

→ 선택 제한을 보여줍니다. 화면의 선택 제한과 서버의 동시 요청 제어를 구분해 설명합니다.

**별도로 준비한 API 요청으로 충돌을 시연하는 경우:**

ここで、同じ会議室の同じ時間帯に、もう一度予約を送ります。
409の競合エラーが返り、重複した予約は登録されません。

→ 사전에 준비한 요청을 실행하고 실제 409 응답을 확인한 뒤 결과를 설명합니다. 별도 요청을 준비하지 않았다면 이 부분은 생략합니다.

### ⑤ 취소

続いて、この予約をキャンセルします。
キャンセルすると、この時間帯が再び空きとして表示されます。

→ 예약 취소 후 빈 시간으로 바뀌는 것을 확인합니다.

### ⑥ 같은 시간대 재예약

最後に、同じ時間帯をもう一度予約します。
このように、キャンセルした時間帯を再利用できます。
以上でデモを終わります。

→ 같은 시간대로 재예약하고 성공을 확인한 뒤 17페이지로 돌아갑니다.

**한국어 뜻**

실제 화면에서 회의실과 날짜를 선택하고 빈 시간을 예약합니다. 정보를 다시 조회해 저장된 예약을 확인합니다. 예약된 시간은 화면에서 선택할 수 없다는 점을 보여주고, 동시 요청 제어는 앞서 소개한 API 테스트로 확인했다고 설명합니다. 별도 API 요청을 준비했다면 실제 409 응답도 보여줍니다. 이어서 취소 후 시간이 다시 비는지, 같은 시간에 재예약할 수 있는지 확인하고 데모를 마칩니다.

**시연 준비 메모:** 시연할 회의실·날짜·빈 시간대를 미리 정해 둡니다. 현재 화면의 예약자명은 고정 표시이며 직접 입력하는 칸은 없습니다. DB 상태를 직접 보여주려면 조회 화면이나 쿼리도 준비합니다. 화면 재조회만 보여줄 경우, DB 내부를 직접 확인했다고 표현하지 않습니다.

**데모가 동작하지 않을 때 사용할 문장:**

申し訳ありません。現在、デモ環境で問題が発生しているため、資料で流れをご説明します。
予約の登録、再取得、キャンセル、同じ時間帯への再予約という順番で確認する内容です。
重複予約への対策については、先ほどご紹介したテスト結果をご覧ください。

한국어: 현재 데모 환경에 문제가 있어 자료로 흐름을 설명하겠습니다. 예약 등록, 재조회, 취소, 같은 시간 재예약 순서로 확인하는 내용입니다. 중복 방지는 앞서 소개한 테스트 결과를 참고해 주십시오.

## 17페이지 — 工夫した点・苦労した点

**일본어 발표문 · 약 55초**

ここで、制作中に工夫した点と苦労した点をお話しします。
工夫した点は、予約のルールをドメイン層にまとめ、Webやデータベースの処理から分けたことです。
保存方法を変える場合も、主にアダプター側で対応できる構成にしました。
また、変更後のテストから配備までをGitHub Actionsで自動化しました。

苦労したのは、開発環境と本番環境の設定を整えることです。
Docker Composeと環境変数を整理し、PostgreSQLのポート競合やFlywayとJPAの設定を調整しました。
さらに、サーバーの再起動後もランナーが動くように設定し、並行リクエストのテストで重複予約が起きないことを確認しました。

**한국어 뜻**

제작 과정에서 공들인 점과 어려웠던 점을 말씀드리겠습니다. 예약 규칙을 도메인 계층에 모으고 웹·DB 처리와 분리했습니다. 저장 방식을 바꿀 때도 주로 어댑터 쪽에서 대응할 수 있도록 구성했습니다. 코드 변경 후 테스트부터 배포까지는 GitHub Actions로 자동화했습니다. 어려웠던 점은 개발·운영 환경 설정을 정리하는 일이었습니다. Docker Compose와 환경 변수를 정리하고 PostgreSQL 포트 충돌, Flyway·JPA 설정을 조정했습니다. 서버 재시작 후에도 러너가 동작하게 설정했으며, 동시 요청 테스트로 중복 예약이 발생하지 않는지 확인했습니다.
