## 1. 작품 소개 — 약 30초

### 일본어 발표문

それでは、私が制作したオリジナル作品「Reserve Hub」についてご紹介します。

Reserve Hubは、会議室などの共有リソースを時間単位で予約するためのシステムです。今回のデモでは社内会議室の予約を例として実装しました。

この作品では、単純に機能を増やすことよりも、重複予約を安全に防止することと、外部技術の変更に強い構造を作ることを重視しました。

### 한국어 의미

제가 제작한 Reserve Hub를 소개하겠습니다. 회의실 같은 공유 자원을 시간 단위로 예약하는 시스템이며, 기능 수보다 중복 예약 방지와 변경에 강한 구조를 중시했다고 설명합니다.

### 발표 포인트

- 제목을 단순한 `会議室予約システム`보다 `予約基盤`이라고 설명합니다.
- 처음부터 “왜 만들었는가”를 이야기한 뒤 기술 설명으로 넘어갑니다.

## 2. 해결하려고 한 문제 — 약 35초

### 일본어 발표문

予約システムでは、複数の利用者が同じリソースと時間帯を同時に選択する可能性があります。

アプリケーションだけで空き状況を確認すると、確認直後に別のリクエストが入ることで、重複予約が発生する可能性があります。

そこで、このプロジェクトではアプリケーションの事前確認に加えて、PostgreSQL側でも重複を防止する構成にしました。

### 한국어 의미

여러 사용자가 동시에 같은 자원과 시간을 선택할 수 있으며, 애플리케이션 검사만으로는 검사 직후 다른 요청이 들어오는 경쟁 상태가 발생할 수 있다고 설명합니다. 이를 DB에서도 최종 보호한다고 말합니다.

### 강조할 문장

> アプリケーションとデータベースの二つの段階で重複予約を防止しています。

## 3. 헥사고날 아키텍처 — 약 55초

### 일본어 발표문

システム構成には、ヘキサゴナルアーキテクチャを適用しました。

中心には、予約や予約期間などのドメインモデルがあります。その外側に、予約登録、照会、キャンセル、空き状況確認といったユースケースを配置しています。

Webからの入力はInput Portを通してユースケースへ渡され、データの保存はRepository Portを通してJPA Adapterへ渡されます。

この構造によって、ドメインロジックはSpring MVCやJPAに直接依存しません。そのため、データベースや入力方式を変更する場合でも、中心となる予約ルールへの影響を小さくできます。

### 한국어 의미

도메인을 중심에 두고 Web과 DB를 어댑터로 분리했으며, 변경의 영향을 줄이고 단위 테스트하기 쉽게 만들었다고 설명합니다.

### 화면 동작

- 페이지 하단의 `システム構成`을 가리킵니다.
- `Calendar UI → REST Controller → Use Case → Domain → JPA・PostgreSQL` 순서로 천천히 읽습니다.

## 4. 핵심 기능 설명 — 약 35초

### 일본어 발표문

主な機能は、予約登録、予約照会、予約キャンセル、そして空き状況の確認です。

予約状態はCONFIRMEDとCANCELLEDの二つで管理しています。キャンセル時にはデータを削除せず、状態だけを変更します。

そのため、キャンセル履歴を残しながら、その時間帯を再び予約できるようになっています。

### 핵심 용어

- 예약 완료: `予約確定` 또는 `CONFIRMED`
- 예약 취소: `予約キャンセル` 또는 `CANCELLED`
- 중복 예약: `重複予約`
- 예약 가능 여부: `空き状況`

## 6. 테스트와 배포 — 약 45초

### 일본어 발표문

品質を確認するために、ドメインの単体テスト、アプリケーションサービスのテスト、PostgreSQLとの統合テスト、そしてREST APIのテストを作成しました。

また、GitHub Actionsを利用して、コードをPushすると自動的にテストとビルドが実行されるようにしました。

テストが成功した場合だけ、Oracle Linux上のSelf-hosted Runnerが成果物を取得し、Spring Bootアプリケーションを自動的にデプロイします。

デプロイ先では、Nginx、systemd、Docker上のPostgreSQLを利用しています。

### 짧은 버전

발표 시간이 부족하면 다음 두 문장만 말합니다.

> 単体テストからREST APIの統合テストまで作成し、全体の回帰テストを実行しています。また、GitHub Actionsを利用して、テストに成功した成果物だけをOracle Linuxサーバーへ自動デプロイする構成にしました。

## 7. 개발 중 문제 해결 경험 — 약 35초

### 일본어 발표문

デプロイ環境の構築では、Self-hosted Runnerの認証失敗や、SELinuxによるsystemdとNginxの通信制限が発生しました。

エラーメッセージだけで判断せず、Runnerの診断ログ、chronyの時刻同期状態、SELinuxの監査ログを確認して原因を特定しました。

SELinuxを無効にするのではなく、実行場所と必要な権限だけを修正して解決しました。

### 강조할 부분

- `chmod 777`이나 `setenforce 0`으로 우회하지 않았다는 점
- 로그에서 root cause를 찾았다는 점
- System Engineer 지향점과 가장 잘 연결되는 경험

### 일본어 발표문

現在の画面では、一日分の各時間帯について空き状況APIを呼び出しています。小規模なデモでは分かりやすい方法ですが、実際の運用では、一日の予約情報を一度に取得するAPIへ改善したいと考えています。

# 예상 질문과 답변

## Q1. なぜヘキサゴナルアーキテクチャを選びましたか。

> 予約の重複確認や状態変更といったビジネスルールを、Springやデータベースの実装から分離したかったためです。また、ポートを基準に依存関係を整理することで、単体テストを作りやすくし、将来データベースや入力方式を変更する際の影響を小さくできると考えました。

## Q2. 小規模なシステムに対して構成が複雑ではありませんか。

> はい、単純なCRUDだけであれば、一般的な三層構造のほうが実装量は少なくなります。今回はヘキサゴナルアーキテクチャを学習し、変更の影響範囲を実際に確認することも目的だったため採用しました。実務では規模や変更可能性を考慮して選択します。

## Q3. 同時に予約リクエストが来た場合はどうなりますか。

> アプリケーションサービスで事前に重複を確認しますが、それだけでは同時実行時の競合を完全には防げません。そのため、PostgreSQL側にも重複予約を防ぐ制約を設定し、最終的な整合性をデータベースで保証する構成にしています。

## Q4. なぜ予約をDELETEしないのですか。

> 予約履歴を残し、後から状態を確認できるようにするためです。削除ではなくCANCELLEDへ状態を変更し、重複確認では確定済みの予約だけを対象にしています。

## Q5. データベースを変更できますか。

> アプリケーション層はRepository Portだけに依存しているため、別のAdapterを実装すれば保存技術を変更できます。ただし、現在の重複防止制約はPostgreSQLの機能にも依存しているため、他のデータベースへ変更する場合は同時実行制御方式を再設計する必要があります。

## Q6. なぜReactではなくHTMLとJavaScriptを使いましたか。

> 制作期間が限られていたため、フロントエンド基盤を追加するより、予約ロジック、テスト、デプロイまで完成させることを優先しました。静的ファイルをSpring Bootと一緒に配布することで、ビルドとデプロイも一つにまとめました。

## Q7. 空き状況のAPIを時間ごとに呼ぶと負荷が高くなりませんか。

> はい、現在はデモとして分かりやすさを優先した実装です。運用規模では、会議室IDと日付を受け取り、一日分の予約一覧または空き時間を一度に返すAPIへ変更します。

## Q8. 一番苦労した点は何ですか。

> アプリケーションの実装だけではなく、Oracle Linux上でCI/CDを動作させる部分です。Runnerの認証失敗やSELinuxによる実行・通信制限が発生しましたが、診断ログ、時刻同期状態、監査ログを確認して原因を特定し、セキュリティ機能を無効にせず解決しました。

## Q9. 次に追加したい機能は何ですか。

> 最初に日単位の一括予約照会APIを追加したいです。その後、認証・認可、ユーザー別予約一覧、会議室情報の管理、HTTPS、監視機能を追加したいと考えています。
